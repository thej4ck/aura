# 0006. Internazionalizzazione

Stato: accettata · 2026-10-21

## Contesto

Oggi il sito è solo in italiano, ma le lingue sono un'evoluzione prevedibile (famiglie, scuole, altri paesi).
Aggiungere una lingua non deve richiedere di riscrivere componenti o contenuti.

## Decisione

- **Testi dell'interfaccia** con [Paraglide JS](https://inlang.com/m/gerre34r/library-inlang-paraglideJs): messaggi in `messages/<lingua>.json`, compilati in funzioni tipizzate (`m.nome_messaggio()`), senza costo a runtime. Nessuna stringa scritta direttamente nei componenti.
- Oggi c'è solo `it` (`project.inlang/settings.json`).
- Strategia di Paraglide `['globalVariable', 'baseLocale']`: niente cookie, niente localStorage, niente prefisso negli URL. In futuro la lingua verrà dalle preferenze del profilo (`preferenze.lingua`).
- **Testi delle lezioni** nei dati del modulo, non in `messages/`: oggi il modulo è scritto in italiano in `modulo.ts`. Una futura traduzione sarà un file **`modulo.<lingua>.ts`** con la **stessa struttura di id** (competenze, attività, schede, widget); un test ne verificherà l'uguaglianza strutturale con `modulo.ts`. Gli id non si traducono mai.
- I nomi delle note (solfeggio o lettere) sono una preferenza separata dalla lingua.

## Conseguenze

- Aggiungere una lingua: un file `messages/<lingua>.json`, la lingua in `project.inlang/settings.json`, i file `modulo.<lingua>.ts` dei moduli tradotti.
- Una traduzione incompleta o disallineata fa fallire il test strutturale invece di rompere un'attività a runtime.
- Se servirà un URL per lingua (per esempio per i motori di ricerca), si aggiunge la strategia `url` di Paraglide senza toccare i componenti.
- La build di Paraglide scarica i plugin di inlang da `cdn.jsdelivr.net`: succede solo in build e in CI, mai nel browser di chi usa il sito.
